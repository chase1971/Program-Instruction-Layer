Macro App: why the .bat launch feels worse than the App Dashboard

And what a fix would let you do with VoiceAttack. Written 2026-09-06.

One-off explainer page in agent docs/scratch/ — not maintained. If the launchers change, this page will quietly go stale.

1. The whole answer in one paragraph

A .bat file is a script, not a program. Windows has no way to run a script except to first open a black console window and type the script's lines into it. That window exists before line 1 of the batch file runs, so nothing inside the batch file can prevent it.

The App Dashboard is a program that is already running. When you click a tile, it starts Macro App from inside itself and pipes the output to a log file. There is no script, so there is no console for Windows to open. That is the entire difference — the app that gets launched is identical either way.

App Dashboard tile → no window

  • App Dashboard (already running Electron process)
  • processManager.ts calls Node's spawn()
  • output piped to SchoolLaunch\logs\macro-app.log
  • npm run dev → Vite → Electron window
Nothing ever appears on screen but Macro App.

Double-clicked launch.bat → window

  • Windows opens a console window to host the script
  • launch.bat runs its cleanup lines in view
  • launch-app-invoke.bat → launch-app.ps1
  • npm run dev → Vite → Electron window
Console sits there ~7.5 seconds, then closes.

2. Second by second — what you are actually watching

launch.bat

what VoiceAttack does today

This is the path with the black box. Every line below is happening inside that window.

  • 0.0 sWindows opens the console window — the black box appears
  • 0.0 snetstat -ano | findstr ":5328" — look for a leftover Vite server
  • 0.1 staskkill /F anything found on port 5328
  • 0.3 → 2.3 sping -n 3 127.0.0.1 — a deliberate 2-second stall so Windows can release the socket
  • 2.3 sdelete renderer\.vite-dev-port so the new Vite publishes a fresh port
  • 2.3 shand off to launch-app.ps1, which starts npm run dev hidden
  • 2.5 → 7.5 sStart-Sleep -Seconds 5 — the script pauses 5 seconds "so you can read the output"
  • ~7.5 sscript ends → launch.bat ends → the console had nothing left to host, so it closes
  • ~7.5 sVite is up by now, so Macro App's loading animation appears right about here
That last pair is exactly what you described: "the cmd prompt closes when the loading animation happens." It is coincidence, not cause. The console closes because the script finished counting to five.

App Dashboard tile

the one that feels instant

No script, no port check, no stall, no pause.

  • 0.0 sDashboard spawns npm run dev with stdout/stderr piped to a log file
  • 0.0 sBecause the output is piped, the helper cmd has no console to draw — invisible
  • ~2 sVite up → Electron opens → loading animation
Zero seconds of anything on your screen except Macro App.

Shift+F5 — the toolbar's "launch default school app"

the hotkey you already have

This is the important one, and it is the part I do not think you realised. It behaves the same as the Dashboard tile, and it does not need the Dashboard to be open.

  • 0.0 selectron-toolbar (always running — it's your dwell host) catches the hotkey
  • 0.0 sdefault-app-launcher.js reads which app is pinned as default
  • 0.1 sschool-app-spawn.js spawns npm run dev with piped output — same trick, no console
  • ~2 sElectron opens → loading animation
Zero seconds of console. Works whether the App Dashboard is open or closed.

3. Why Shift+F5 isn't already doing what you want

Because it is currently pinned to Factoring, not Macro App.

The pin lives in one small file — App Dashboard\config\default-app-settings.json — and right now it contains:

{ "defaultAppId": "factoring" }

Change that one word and Shift+F5 launches Macro App, console-free, from VoiceAttack, forever. You set it by right-clicking the Macro App tile in the Dashboard and choosing "set as default" — no file editing.

So the reason "connecting VoiceAttack to the launcher isn't as good" is not that the hotkey system is weaker. It is that you pointed VoiceAttack at the .bat — the one path that is forced to show a window — instead of at the hotkey that was already built to avoid it.

4. The one thing the .bat does better

Worth knowing before you throw it away. Macro App's Vite server is configured with strictPort: true on port 5328, which means: if an old Vite is still holding that port, the new one refuses to start rather than picking a different port — and Macro App can end up showing you stale code. The three paths handle that very differently:

Launch path Clears a stuck port 5328? Deletes the port handshake file? Console?
launch.bat Always kills any listener, no questions asked Yes Yes, ~7.5 s
Shift+F5 / Launcher Panel tile Only if the port isn't already answering as Macro App No — but dev-electron.cjs deletes it itself None
App Dashboard tile Never checks No — same, the dev script covers it None
In practice the middle row is fine: scripts\dev-electron.cjs deletes the handshake file on every start anyway, and a genuinely stuck port is rare. The batch file's cleanup is belt-and-braces from a day it bit you. If we drop the .bat and you ever see stale code again, the fix is to add that unconditional kill to whichever path you end up using — not to go back to the console.

5. Three ways to get a dedicated Macro App launch

Option 1 · recommended

Pin Macro App as the default app

No code. Two clicks.
  • VoiceAttack sends Shift+F5 — done.
  • Zero console. Identical to the Dashboard tile.
  • Works with the Dashboard closed.
  • Costs you the "pick any app" slot — Shift+F5 stops launching Factoring.
  • Other apps still launch from the 📚 Launcher Panel grid.
You get: one voice command that opens Macro App instantly and silently, today, with nothing to build.
Option 2

Hide the .bat behind a .vbs

Tiny: one 2-line script file.
  • Keeps the aggressive port-5328 cleanup.
  • No console — .vbs can run the batch fully hidden.
  • Leaves Shift+F5 free for picking other apps.
  • Still has the 2 s stall + 5 s pause internally, so it's slower to finish — though you'd see nothing. I'd set the 5 s pause to zero at the same time.
You get: the most reliable launch, silently, on its own VoiceAttack command — without giving up your pick-an-app hotkey.
Option 3

A second toolbar hotkey wired straight to Macro App

Real change: toolbar hotkey map + handler.
  • A dedicated hotkey that is only Macro App and can never be re-pinned.
  • Zero console, same spawn path as Shift+F5.
  • Shift+F5 stays a pick-any-app hotkey.
  • Adds a new mechanism to the toolbar, which is the thing your own rules say to avoid unless the existing one genuinely can't do the job.
You get: both hotkeys at once, at the cost of code I'd have to write and you'd have to remember exists.

My read: you said you use Macro App so much that you want the hotkey dedicated to it. If that's true, Option 1 is free — the "pick an app" flexibility is worth nothing to you if you always pick the same app, and the Launcher Panel grid already covers the occasional Factoring launch.

Go with Option 2 instead if you want to keep Shift+F5 pointed at whatever you're teaching that week and give Macro App its own separate voice command.
