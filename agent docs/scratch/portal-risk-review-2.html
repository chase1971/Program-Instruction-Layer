1. Broken, but switched off for students

Confirmed against the live database. You have Matrix turned off for 30 students in M1324 on purpose, so no student is hitting this today.

Before Matrix goes back onHappens on its own

The Matrix tutorial can't save or submit since migration 033

Migration 033 (multi-section testers) added a new check to the function that saves progress: the activity's class has to match the student's class, or the save is refused with "Activity not available for this class."

That works for exit tickets, because each one belongs to a class. The Gauss-Jordan tutorial doesn't belong to any class. It was registered with no section, on purpose, so every section could use it. Its empty section never matches a real one, so every save is refused.

What a student sees: the "offline" note while they work. When they press Finish, the portal saves first, and that save fails too, so the tutorial can never be submitted. Your console will show nobody completing it.

Who hits it today: only CHASE1 and the two shared tester codes, because they skip the per-student switch. Turning Matrix back on for students brings everyone into it.

Worse: the portal retries a failed save immediately with no pause (see "A failed save retries instantly" below), so every phone with the tutorial open keeps hammering the database.

What to do

A small follow-up migration: only require the class to match when the activity actually names one. The tutorial submit function (022) already does exactly this, so it's copying an existing rule, not inventing one. It's safe to push right away, and nothing needs a Netlify deploy.

student-session-kit/supabase/migrations/033_multi_section_testers.sql (save_attempt_progress) · live: activities.section_id is null for matrix/gauss-jordan

2. Doors that are open

Low stakes by your standard for grades, but the first one can destroy data, and nothing on the free plan can bring it back.

Fix firstNeeds someone trying

Teacher-only database functions can be run by anyone with the website address

Every "teacher only" function in the migrations was locked with the same line, which takes access away from "the public." But Supabase also hands the website's key its own separate permission on every new function, and nothing ever took that one away. The key that ships inside the portal can still run everything.

I confirmed this on the live database, and then with nothing but that public key (read-only, counting rows without printing them). The key could read your class ids straight from the activities list, and use one to pull the login log with student ids in it.

So someone with only the site address, and no student code, can:

  • Delete any student's work, or a whole class's in a loop (reset_student_attempts)
  • Lock students out (revoke_student_code, which has no undo button)
  • Post an announcement to your class. It only needs the course name (MATH-1324 4202 1) and the word current.
  • Unpublish or edit exit tickets, change who can open an app, and move CHASE1's preview class

It needs a person who goes looking. But the announcement one gets their words onto every student's home screen under your name, and the delete one can't be recovered (see “No backups” below).

What to do

One migration that removes the website key's access to the 15 teacher functions, and changes the default so any function added later starts locked. The portal never calls any of them, and Macro App uses its own key, so it's safe to push right away with no deploy.

Open today: reset_student_attempts, revoke_student_code, publish_exit_ticket, update_exit_ticket, unpublish_exit_ticket, publish_class_announcement, unpublish_class_announcement, set_student_app_access, set_students_app_access, list_student_app_access, list_portal_login_events, grant_device_bind_override, set_preview_section, revoke_student_membership, finish_attempt

3. Things that turn into emails to you

Your "does this generate an email to me" test.

Before next termHappens on its own

Every returning student gets locked out at the start of next term

A phone remembers the first code it signed in with. When a different code's link opens on it, the portal shows "You can't use someone else's link," as long as the remembered code still works.

Nothing ever turns off last term's codes. So a student who takes you again next term gets a new code, opens the new link on the same phone, and is blocked, because their old code is still active. Same for a student in two of your sections at once, since codes are per course.

Force link (migration 030) does unstick them, but only after they email you and you press it for that student. That's one email per returning student, which is the exact thing you're trying to avoid.

What to do

Either of two small changes. (a) When you retire a course, turn off its codes in the same step, so an old code on a phone clears itself silently. (b) Treat a remembered code from a retired course as not a conflict. Option (a) fits what you already do at term end and needs no portal change.

student-portal/src/hooks/useStudentIdentity.ts (mismatch branch) · Macro App course retire flow

Worth fixingHappens on its own

A failed save retries instantly, forever

When saving progress fails, the portal puts the save back in line and tries again immediately, with no waiting in between, and it never gives up.

  • Phone offline (walking between buildings): each try fails in a split second, so the page spins through thousands of tries and drains the battery until the signal comes back.
  • The database refuses the save (like the Matrix problem above): it keeps re-sending the same doomed save for as long as the tab is open, even after the student leaves the quiz.

This is why the Matrix problem is worse than "the tutorial doesn't save": every open tutorial is a phone stuck in this loop.

What to do

Wait before retrying, and wait longer each time (1 second, then 2, then 4, up to about 30). Stop retrying a save the database refused, as opposed to one that couldn't reach it. Stop when the student leaves the page. It's all in one file. It needs a Netlify deploy.

student-portal/src/hooks/useResumableAttempt.ts (flushSaveNow → finally block)

4. Worth knowing

Know about itHappens on its own

No backups, and the database goes to sleep after a quiet week

Backups: Supabase's free plan gives you no backup you can restore from. Anything deleted, by the open doors above or by a teacher-side mistake, is gone.

Sleep: free projects pause after about 7 days with no activity. Over winter break every student opening the portal would get the "You need your class link" screen, and it stays that way until you restore the project in the Supabase dashboard.

What to do

A scheduled data dump to your PC (the Supabase command line already on this machine can do it), maybe weekly. For breaks, either remember to wake it up before classes restart, or let the same scheduled job keep it active.

Deactivate and the class gate are only checked in the browser

The roster Deactivate toggle and the "Matrix is only for M1324" rule are enforced by the portal page, not the database. A student who knows how can skip both by setting one value in their browser's storage (mathapps.isInstructor) or adding ?previewSection= to the address. Deactivate never stopped a student on the database side anyway.

By your standard this probably doesn't matter. It's here so "deactivated" isn't mistaken for "blocked."

What to do
