Macro App plan, in plain language

What the plan is trying to do, without the code details.

The goal in one sentence

Do all the loading while the splash screen is up, so that once the app appears, everything you click is already there, with no waiting and no "starting…" messages.

The three rules the plan follows

1. Wait at the start, not during use

A longer launch is fine. Hiccups when you click a tab, a course, or the student preview are not. Using more memory to keep things loaded is fine.

2. One traffic controller for all the browsers

The app has many little built-in browsers (D2L, Pearson, gradebook pages, the student preview). Instead of each part of the app loading pages on its own and tripping over the others, one controller handles every page load. Parts of the app just say "I need this page" and the controller handles it.

3. No doing the same job twice

Where two pieces of the app do the same thing, combine them, or write down why both are needed.

Where things stand today

Already working

  • The traffic controller exists and every browser already goes through it.
  • Gradebook courses load in the background, and the splash can wait for them.
  • Each visible tab gets its page loaded in the background after you're signed in.
  • The student preview refreshes reliably and shows the right class.
  • Crashes and errors get logged where you can see them.

Still causing hiccups

  • The student preview server doesn't start until you open the preview.
  • That server also throws away its saved work every time, so it starts slow.
  • The splash only waits for gradebook. Other tabs may still be loading when the app appears.
  • Tabs like Managing Grades only have your current course ready. Switching courses there loads on click.
  • Four different pieces each do their own warm-up, with no one in charge.

The steps, in order

1Have the student preview ready at launch You'll feel this most

Start the student portal preview while the splash is up, and stop it throwing away its saved work every time, so it starts fast. Also load the preview page itself in the background.

What you'll notice: open Teacher Console → Preview and the phone is already showing the portal. No more "Starting preview server…".

2One warm-up list, and the splash waits for it You'll feel this

Combine the four separate warm-ups into one list of everything that should be ready: gradebook courses, every visible tab, the student preview, and the background servers. The splash stays up until that list is done. If something is very slow, the app opens anyway after a time limit you choose.

What you'll notice: right after the splash closes, every tab you click is already loaded.

3Keep every course ready in the other course tabs Your call

Today only gradebook can keep all your courses loaded. This would do the same for tabs like Managing Grades and Managing Dates, so switching courses there is instant too. It uses more memory, so you'd decide whether it's worth it and which tab to do first.

4One honest answer to "is this page ready?" Behind the scenes

Right now gradebook keeps its own separate list of which pages are ready, apart from the main list. Merge them into one. Also make every browser action report clearly whether it worked and, if not, why, instead of sometimes quietly pretending it worked.

What you'll notice: fewer "the button did nothing" moments, and clearer messages when something can't load.

5Make the traffic controller the only way in Behind the scenes

Today the app still has a second, older line for loading pages alongside the traffic controller. When the two get mixed up you get freezes, like the September Pull freeze. Move everything onto the controller so that line can be retired. Each part of the app will just say "I want this page, shown or hidden" and the controller does the rest.

What you'll notice: race-condition bugs stop coming back every time a new feature is added.

6Student preview leftovers Small

Check whether switching between Preview and other screens still flashes. Only if it does, show a still picture during the switch. Tidy up a few small things about how the preview frame lines up.

7General tidying Only when already working nearby

Break up a few files that have grown too big, simplify how the Teacher Console passes information around, and finish small gradebook and Assignment Assistant cleanups. These get done when someone is already working in that area, not as a separate project.

Things that look like duplicates

Keeping both

The two Vite servers. A Vite server is what shows an app's code while you're editing it. One shows the Macro App itself. The other shows your own copy of the student portal, so the preview can show changes you haven't put online yet. They're two separate projects, and the portal has to keep working on its own for Netlify. The plan starts them together at launch instead of merging them. If you're not editing the portal, setting the preview to "Live" means the second one isn't needed at all.

The two calendars. You said earlier they're meant to be different, so they stay separate.

Combining

  • Four warm-up pieces → one warm-up list.
  • Two "is it ready?" lists → one.
  • Two ways of loading browser pages → the one traffic controller.
  • The gradebook-only splash wait → one wait that covers everything.
  • Two places that remember "signed in to D2L" → one.

Things the plan deliberately won't do

  • Load tabs only when you click them. It would make launch faster, but you'd feel the hitch later.
  • Limit how many courses stay loaded. Memory is the price you chose to pay.
  • Switch to an installed version for speed. You change the app constantly, so it stays in edit mode.
  • Rewrite the app in something else. The slowness comes from what the app does, not the tools it's built with.
