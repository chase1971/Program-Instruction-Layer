What the session tracking was actually measuring — and how to build a real baseline

You asked whether the tracking data is worth keeping. Short answer: one part of it was real, three parts were measuring themselves. Here is the whole thing without the code.

Audit of 342 task bumps · 67 sessions · Aug 9 – Sep 9, 2026

Part 1 — Three of the four gauges were broken

Not "slightly off." Each one was reporting on something it physically could not see. Here's each gauge, what it claimed, and what it was really doing.

The gauge said

"Index-first rate: 0%"

Meaning: the agent never once checked your index before going hunting. Across all 233 tasks.

What was really happening

The agent reads AGENTS.md on every single turn — but it arrives automatically, loaded into memory before the agent does anything. It never gets "opened" like a file.

The gauge only counted files that get opened. So it was watching a door that nobody uses, and reporting the room was empty.

Meanwhile: agent docs/INDEX.md was the single most-opened document in the entire log — 102 visits. Your index is being used constantly. The meter just couldn't see it.

The gauge said

"99.2% of searches unexplained"

Meaning: the agent ran 4,813 searches and hid almost all of them from you. Sounds like dishonesty.

What was really happening

Every logged step has a label saying what kind of thing it was. The gauge only recognised four labels: grep, glob, web, search.

Agents invented 59 different labels — 21 of them used exactly once. They'd log a search as code or other, because that's what they were searching for.

So the gauge wasn't catching lies. It was catching spelling differences.

The gauge said

"Path coverage: 24%"

Meaning: the agent only wrote down a quarter of where it looked. Another honesty alarm.

What was really happening

It compared steps written down against everything that happened since the last log entry.

But you log once per finished deliverable. Half the time that's 17 minutes. Sometimes it's 9 hours. One entry covered 44 hours.

A 5-step summary of a two-hour stretch scores terribly — and it should. The gauge was measuring how long since you last logged, dressed up as an honesty score.

The one that worked

The index-gap list

When an agent opened one of your docs and it didn't answer the question, that got recorded. That list is real, and it has already paid for itself — it's why rows for Guildrun and the student pipeline got added to INDEX.md.

One catch: about 41% of the flagged "gaps" weren't gaps. Notes like "no narrower recipe was needed" got filed as failures. But confirming that nothing more specific exists is the index succeeding. I've sharpened that rule in the procedure doc.

Part 2 — The surprise: where your tokens actually go

This is the part that changes how you should think about all of it. I measured the real, billed token usage sitting in your session transcripts — data that was on your disk the whole time, unused.

Cutting AGENTS.md in half would save you about 0.6% of your token cost.

Why this happens

Every time the agent replies, it re-reads the entire conversation up to that point. Not just your instructions — every file it opened, every search result, every previous answer.

So the real formula for what a session costs isn't about how good your index is. It's:

how big the conversation got  ×  how many turns it took

Your instruction docs are a rounding error inside the first number.

What this does not mean

It does not mean AGENTS.md doesn't matter. A shorter, sharper instruction doc probably gets followed better — that's a quality argument, and a good one.

It only means: tightening your docs is not a cost lever. You'd been treating it as one. The cost levers are how long sessions run and how much the agent reads along the way.

Part 3 — Why this data can never be a baseline

Even with perfect gauges, the old approach couldn't answer "did my change help?" Here's the reason, and it's not a bug you can patch.

The trap this creates

Here's a real number from your log that shows how badly this misleads:

When the agent…Average searches
Started at your index25.4
Skipped the index17.4

Read literally, that says your index makes things worse. It doesn't. The agent reaches for the index exactly when the task is unfamiliar. Hard tasks send you to the index and cost more searches — the index didn't cause the cost, the difficulty did.

You cannot separate those two things by watching real work. No amount of extra logging fixes it.

Part 4 — How you get a real baseline

You fix it by holding the task still. If the question never changes, then any difference between runs has to come from what you changed.

The difference between the two runs is caused by your change. Nothing else moved.

What a "question" looks like

Plain retrieval questions about your own tree, where you already know the right answer:

"Which file owns the rule for launching a Python app without a visible console?"
"Where does Guildrun Stats store saved runs?"
"What's the rule about modals and clicking outside them?"

Each one runs in a fresh session — no leftover conversation — and the agent is only allowed to look, not edit. Three things get scored:

  1. Did it get the right answer? — the thing that actually matters
  2. How many tokens did it burn getting there? — the real cost
  3. How many looks did it take? — how directly your docs pointed at it

Why this is cheap

Fresh sessions start nearly empty, so each question costs very little. A full 20-question sweep runs roughly the cost of one mid-sized task — and unlike a real task, you can run it again next month and the comparison actually means something.

Part 6 — The one thing to decide

The tracking now measures real cost honestly. The open question is whether to build the fixed-question set that turns it into something you can experiment against.

Option A — Retrieval only ← my recommendation

15–20 "where does this live / what's the rule for that" questions. Cleanest possible signal: it isolates your indexing from everything else, and it's cheap to re-run.

Limit: it tells you whether the agent can find your rules — not whether it then follows them.

Option B — Retrieval plus a few small build tasks

Adds 3–4 fixed little jobs ("add a button to X the house way") scored on whether your rules were actually obeyed. Catches more, but the results are noisier and it costs more, because building the same thing twice never goes identically.

Option C — No probe set; just watch real work more carefully

Add redirect-count and context-growth to real sessions and wait. Cheapest to build. But because of Part 3, you'd need many months before any trend is readable — and it still can't isolate a single doc change.
