Student Portal — how it all connects

Plain-language walkthrough of the grading pipeline you started building: what each piece does, how a student's answers reach your desk, and every weak spot worth knowing about before you build on it.

Written 2026-09-05. Describes the system as it exists tonight: one working app (the Check App Quiz), gated portal live at mathappsclass.netlify.app, Student Progress tab reading results in Macro App. Standalone apps like Transformations are deliberately left out — they will be rebuilt into this pattern later.

The short version

You have four pieces. Math App Studio is where you design an app. The Student Portal is the website students visit, and each app now lives inside it rather than being its own separate site. Supabase is a database on the internet that stores who did what. Macro App is where you read the results, next to real student names.

The clever part of the design — and it really is the right call — is that the database never learns anybody's name. It only knows anonymous codes. The list matching a code to a human being lives on your PC and your Google Drive, and nowhere else.

The four parts

1. Math App Studio
School Scrips\Math App Studio

Where you lay out what an app looks like — buttons, boxes, wording — by dragging instead of describing positions out loud. It produces a design file; an AI turns that into a working app. It has nothing to do with grades or students. It stops once the app exists.

2. Student Portal
School Scrips\student-portal → mathappsclass.netlify.app

The website students open. It checks their code, shows the tiles, runs the app, and sends the results. The Check App Quiz proved the pattern: an app is a folder inside this website, reached by a link like #/check-app, not a separate site you link out to.

3. Supabase (the database)
School Scrips\student-session-kit\supabase\migrations

A database hosted on the internet, holding five tables: the list of apps, the class sections, the student codes, one row per quiz attempt, and one row per question answered. The SQL files in that folder are the blueprint that built it. This is the meeting point — the portal writes here, Macro App reads from here.

4. Macro App — Student Progress tab
School Scrips\Macro App\electron-app\student-progress-io.js

Your side. Reads the attempts out of the database with a master key, then swaps each anonymous code for a real name using the roster files on your Drive. Shows Attempt 1, 2, 3 per student, and you can click any score to see which questions they missed.

Follow one student, start to finish

1
You generate the codes
You run the code generator against a D2L roster. It invents a random ID and a six-character code for each student, writes student-portal-codes.json into that course's Drive folder, and prints a block of SQL.
2
You paste that SQL into Supabase
It loads only the IDs and the codes. Deliberately no names. The database now knows "code K7RM2P is a valid student" and nothing more about them.
3
The student gets a personal link
Something like mathappsclass.netlify.app/?s=K7RM2P. The code in the link is the entire login. No password, no account to create.
4
The portal checks the code
It asks the database "is this real?" If yes, it gets back the anonymous ID, saves the code on that device so they don't need the link again, and wipes the code out of the address bar so a screenshot doesn't leak it. If the code is wrong, they see a locked page instead of the tiles.
5
They take the quiz
One question at a time. When they finish, the portal writes an attempt row, a row per question answered, and marks it complete with a score.
6
They can see their own grades
The Grades tab shows their history — but only theirs. Students have no permission to read the attempts table directly; a single locked-down database function hands back just their own rows.
7
You open Student Progress in Macro App
Macro App pulls the attempts using the master key, loads the Drive files to turn each anonymous ID back into a name, and shows you the roster with each attempt in its own column.

What this design already gets right

No student names or emails in the cloud — at all

The students table has an ID, a code, and two timestamps. That's it. Even if the entire database were handed to a stranger, it would be a pile of anonymous codes and scores with no way to tell who anyone is. The translation list never leaves your PC and your Drive. This is the strongest thing about the whole design and it is worth protecting.

Students are locked out of every table by default

The public key that ships inside the website can't read the student list, can't read the section list, and can't read other people's attempts. The only things it can do are call three specific, tightly scoped functions. That's the right shape.

Made-up codes do nothing

The check function only ever looks a code up — it never creates one. A stranger typing random codes into the address bar can't conjure themselves an account.

Guessing codes isn't realistic

Six characters from a 32-letter alphabet, with the confusable ones like I, O, 0 and 1 removed, is about 1.07 billion combinations. With roughly 35 codes live, a random guess hits about once in 30 million tries. Not a practical way in.

No keys are sitting in your code repositories

I checked every tracked file in both projects. Only example files with placeholder text. The real keys live in Netlify's settings and in a single ignored file on your PC.

Weak spots, worst first

None of these are on fire. But you asked where the problems are before you build on top of it, and this is exactly the right moment to ask, because two of them get much more expensive to fix later.

1. The student's browser decides its own grade
Serious — if it counts for points

What's actually happening

The quiz is marked on the student's own computer, and then their computer tells the database what score to record. The database writes down whatever number it's handed. It has never seen the questions and has no idea what the right answers are.

What that means in practice

A student who knows how to open the browser's developer tools can report a perfect score without answering anything. Separately, the correct answers are shipped inside the webpage itself, so a curious student can simply read the answer key before starting.

How much you should care

For a "did you find the portal and click through it" check, not at all. The moment any of this counts toward a real grade, this is the whole problem — everything else on this page is a footnote next to it.

What fixing it looks like

The answer key moves into the database, and the app sends what the student picked instead of what they scored. The server marks it. That's a new table for questions and answers, a new server function, and a change to how apps submit. Worth designing now, while there's one app, rather than after there are eight.

Position taken 2026-09-06

Accepted for anything ungraded; fixed before anything is graded. This becomes the three grading modes described further down. A warm-up or a self-check can keep marking in the browser, where the worst case is a student fooling themselves. Anything worth points keeps its answer key in the database, where the browser never sees it — so there is nothing to read and nothing to edit. The judgement that few students will think to try this is reasonable, but it is not what the graded path relies on.

2. Nothing checks that you are who you claim when saving a result
Moderate

What's actually happening

The rule that lets the portal save an attempt is literally "allow it." The student's ID is just part of the message being sent, and nothing verifies it matches the code that was actually used to get in. The same is true when reading grades back: the function hands over whatever student's history you ask for, without checking it's yours.

What that means in practice

If someone got hold of another student's internal ID, they could file results under that person's name, or read their grade history. Those IDs are long random values that never appear in the link, so this isn't something anyone stumbles into — it needs deliberate effort and a leaked ID.

What fixing it looks like

Tie the session to the code that was claimed, so the database enforces "you may only write and read your own rows" instead of trusting the message. Naturally solved at the same time as problem 1, since both come down to the server not verifying what it's told.

Position taken 2026-09-06

Worth separating the two halves, because only one is fixable. The technical half — the server trusting an ID it was handed — is a real bug and gets fixed alongside problem 1. The human half — a student simply giving their link to someone else — is not solvable and is accepted. It is the same exposure every homework platform has, where a student can hand over their password. Nothing short of proctoring closes it, so it isn't treated as a defect here.

3. A student who drops keeps their access
Moderate — will actually happen

What's actually happening

When you regenerate codes after a drop, the roster file on your Drive marks that person as dropped. But their row in the database is untouched, so their code still works and their saved link still opens the portal. There's also no way to turn a code off, and nothing stops a student forwarding their link to somebody else.

What fixing it looks like

Small: add an "active" switch to the student row, have the check function refuse inactive ones, and have the generator turn off anyone marked dropped. This one is cheap and worth doing early, because unlike the others it's guaranteed to come up every semester.

Position taken 2026-09-06

Agreed and queued — a dropped student's code just gets switched off. Worth noting the one wrinkle: prefer deactivating the row to deleting it, so the attempts that student already submitted stay attached to something and their past scores don't turn into orphans.

4. Your FERPA document no longer matches reality
Fixed — 2026-09-06

What was happening

That document is the thing your college would read to decide whether your setup is acceptable. It stated that all student records stay on your machine and that nothing is uploaded to cloud storage. As of this week, quiz scores go to Supabase.

Why it was fixable on paper alone

Your actual design is stronger than the document described, not weaker — what goes to the cloud is anonymous, and the identifying half never leaves your PC. The document just had to say so. The risk was never the system; it was being asked about it and handing over a description that's out of date.

What was done

Macro App\docs\FERPA_DATA_HANDLING.md now describes the split accurately: de-identified scores in Supabase, every identifiable record still local. It also lists the safeguards behind that — row-level security, the locked-down database functions, and how the master key is stored — and records "student names in Supabase" as a hard constraint that is never to be crossed.

5. Neither project is backed up anywhere
Fixed — 2026-09-06

What was happening

Both the portal and the database blueprint existed only on this PC. No GitHub, so no off-machine copy, no history to roll back to, and no way to work on them from the laptop. Everything else you own was backed up; these two were not.

What was done

Two private repositories now exist and both are pushed: chase1971/student-portal and chase1971/student-session-kit. Same treatment as every other app in the tree — they pull at the start of a session and push at the end.

6. Anyone could flood the database with junk
Low

The public key is inside the website's code, which is normal and unavoidable for this kind of site. With it, somebody could write endless meaningless attempt rows. They still couldn't read anything. The damage would be a cluttered database and possibly hitting the free plan's limits — annoying, not dangerous. Worth a rate limit eventually, not now.

Why that one key can't be made private

This trips everyone up, so it's worth being precise. There are two different keys, and only one of them is public.

The public key (Supabase calls it the anon key) is the address the student's browser dials to reach the database. The student's browser has to know it, or the quiz can't submit anything. Anything a browser knows, a student can read — it's sitting in the downloaded page. There is no version of a website where the browser can talk to a server without knowing how to reach it. So the anon key being visible isn't a mistake or a shortcut; it's what the key is for. Supabase designed it that way, which is why it's paired with row-level security: the key gets you to the door, and the door decides what you're allowed to do. Right now that door allows "write an attempt" and nothing else. It does not allow reading anyone's data.

The master key (the service role key) is the opposite: it ignores every door. It only ever lives on your PC inside Macro App, is never sent to a browser, and as of today is encrypted at rest.

None of this is about GitHub. That's the part worth separating out, because the two got tangled together. Both repositories are private, and they should stay private. The anon key would be visible to students even if your code were locked in a vault, because it ships inside the website they load. Making the repository public or private changes nothing about it either way.

The one place a genuine public-versus-private question came up was the Transformations app, whose build script downloads student-session-kit anonymously during deployment — an anonymous download can't reach a private repository. But you've said Transformations is out of scope and will be rebuilt inside the portal, so that requirement is dead. Everything stays private.

7. The master key is stored as plain text
Fixed — 2026-09-06

What was happening

Macro App kept the Supabase master key in config.local.json in readable text. That key bypasses every protection in the database. It was correctly excluded from version control and sat on an encrypted, password-locked machine, so it was defensible — just noticeably weaker than how you treat your Google Vision key. Same idea, two standards.

What was done

The master key now uses exactly the same mechanism as the Google Vision key: Windows DPAPI, tied to your Windows account, no passphrase to remember. On the next launch Macro App reads the plaintext key once, encrypts it to student-progress-key.enc, and from then on prefers the encrypted copy. After that first run the plaintext line can be deleted from config.local.json and everything keeps working. A copy of that file taken off this machine is then useless to whoever has it.

Problems that aren't about security

Macro App only looks for one specific app

The roster table asks the database for the Check App Quiz by name. The moment you add a second app, its results will land in the database correctly and simply not appear on your screen. This is the first thing to fix when app number two exists, and it will be confusing if you hit it unprepared.

Adding an app currently means editing five separate files

A database entry, a tile in the app list, the app folder itself, a line in the portal's routing, and an entry in the grade-labels file. Nothing enforces that you did all five, and two of them are lists that will quietly fall out of step. Worth simplifying once there are two or three apps and the real pattern is obvious.

The submit code existed twice — resolved 2026-09-06

There was a shared copy in the database project and a hand-typed duplicate inside the portal, because the shared one had no GitHub repository to pull from at the time.

It turned out to be simpler than "merge them." The shared copy was written for the Transformations app — in fact this whole database was originally built for Transformations, which is why the very first migration lists it before anything else. That attempt never worked: back then there were no student codes at all, so nothing recorded who was playing, and the results would have landed attached to nobody. The Google Form stayed the real path the entire time.

So the shared copy had exactly one consumer, and that consumer never needed it. It's now deleted, along with all the database wiring inside Transformations, which goes back to running purely on its completion code and Google Form. The portal's copy is the only one left, and it's the only one anything uses.

The design decided 2026-09-06

Worked out in conversation after the problems above came to light. Written up in full in student-session-kit/docs/STUDENT_PROGRESS_PIPELINE.md.

Questions stop being code and become data

Today the questions live in a TypeScript file, which is why adding an app takes five edits and why you can't write a quiz without an AI writing code for you. Move them into the database and both problems dissolve at once — and the answer key becomes just another column sitting next to the question, which is what makes server-side marking nearly free.

Three grading modes, one switch — not two systems

ModeAnswer keyWhat it's for
NoneThere isn't oneExit tickets, confidence checks, free-response feedback. Nothing to cheat because nothing is scored
BrowserExists, marked on the deviceIn-class warm-ups. You're in the room, and dishonesty earns one participation point in front of you
ServerStays in the databaseHomework and anything carrying real points

One field on the activity. You can flip a quiz from browser-marked to server-marked later without touching a line of app code. A question with no options under it is a free-response box — easy to collect, so don't try to auto-mark it, which puts it naturally in the first mode.

Writing a quiz by pasting

The app has no AI in it. It has a format and a parser; whatever LLM you like does the converting outside. Deliberately not JSON — one missing bracket kills the whole paste, and LLMs love wrapping output in code fences. A star marks the correct answer:

Q: What is the vertex of $y = (x-3)^2 + 4$?
* (3, 4)
- (-3, 4)
- (3, -4)

Q: How confident do you feel about completing the square?
- Got it
- Shaky
- Lost

The format carries the grading mode by itself: stars present means marked, no stars means feedback. Equations use KaTeX, which is already a dependency in six of your projects, so nothing new gets introduced. Always preview before saving — render it exactly as students will see it and list any lines that didn't parse. A silent misparse means a broken quiz in front of a class. And the single most valuable piece is a button that copies the prompt to give your AI; that's what makes the whole thing usable without typing.

Where authoring lives

Macro App, not the portal. It's private, it already holds the master key, and it's already where you go to look at results. The app itself is the login, so there's nothing to build.

Letting other teachers use it

The shape that keeps the privacy design intact

Every teacher runs Macro App with their own roster files, so no student name ever enters the database for anyone — not just for you. One shared database, with every row recording who it belongs to. That owner column is nearly free to add now and a painful migration later, so it goes in from the start even while you're the only teacher.

Separate Netlify addresses are optional, not required — who you are is decided at sign-in. Handing over the desktop half is already a solved problem: Macro App has a slim distribution build meant for exactly that.

Two things that bite when the second teacher arrives

Emailing personal links is half built. The code generator already writes a CSV with each student's email and their own link, and Macro App already drives Outlook. But the existing path puts everyone in Bcc, which is the wrong shape when every link differs — it needs a mail-merge, one message per student.

Codes have to be unique across the whole database, but the generator only checks the codes in your own local roster file. Two teachers can mint the same one, and the second person's paste fails. It fails loudly rather than corrupting anything.

Decided 2026-09-06 — give each teacher their own prefix. Rather than asking the database every time a code is minted, each teacher gets a short tag that leads every code they issue. Two teachers then cannot collide, because the prefixes differ before the random part even starts. It needs no network call, it keeps code generation working entirely offline, and it makes any code self-identifying at a glance. The only thing it costs is that prefixes have to be handed out centrally — a one-line list, not a system.

The blocker, named — and not being solved yet

The moment you host another instructor's student records, you personally become the custodian of them. At a college that's normally something the institution signs off on rather than something an instructor arranges privately. Not a reason to avoid it — a reason not to end up there by accident.

Position as of 2026-09-06: this is the real obstacle to a second teacher, and it is understood as such. Prefixes solve collisions; they don't solve the fact that a shared database you control means you can read their rows. Solving it properly means either a separate database per teacher or restrictions that apply to you too. Deliberately deferred — nothing should be built toward multi-teacher beyond the owner column until this gets an answer.

The one thing to take away

The privacy design is genuinely good, and better than most things a school would buy — no student's name ever reaches the internet. What isn't built yet is trust: the system currently believes whatever a student's browser tells it. That's completely fine for a click-through check, and it's the thing to fix before a single point of anybody's grade depends on it.
