Recipes Review RESOLVED 2026-08-08

Every interaction recipe in agent docs/recipes/ checked against the live code that backs it — not just whether the exemplar file exists, but whether the function, class, or value it names is still there and still does what the recipe says. This is INSTRUCTION_LAYER_AUDIT.md § 2g (doc vs. code) run recipe-by-recipe, the highest-yield check because a recipe can be internally consistent and simply wrong about the code — nothing else catches that. The findings below are the original doc-vs-code pass and are kept as historical record — Chase then walked through all 12 "needs rework" items in real-usage terms (does he actually reference this as a recipe, not just is it accurate), which changed several outcomes from what a pure accuracy pass would have done. See the outcome box below.

Outcome (2026-08-08, three rounds): of the original 26, only 3 recipes are still in the shared agent docs/recipes/ folder — modal-shell.md, canvas-kit-target-size.md, tutorial-flash-vocabulary.md — each confirmed genuinely cross-app (10, 7, and 5 consuming apps respectively). Original findings (2026-08-08, before the app-folder split)

Verdict: no dead recipes and no missing exemplars — every file still pointed at real code. The problem was narrower and sneakier: stale or invented numbers. Several recipes restated a timing value instead of naming the constant (the one rule the folder leads with), and a few of those numbers were flat wrong — not just against the rule, but factually stale versus what the code did. Two files (modal-shell.md, state-machine.md) went further and described a hook, state, or import path that was never real. The cards and table below are that original pass, kept as historical record — they predate the app-folder moves in the table above, so a filename here may no longer live in agent docs/recipes/.
Not covered on this page: the 6 code-shape standards that live in the same folder — CODING_STANDARDS.md, INIT_NEW_APP.md, file-headers.md, react-patterns.md, refactoring-checklist.md, anti-patterns.md. Those were reviewed and reworked yesterday (2026-08-07) as part of the cursor-patterns/ elimination — see that review and agent docs/sessions/SESSIONS.md. This page is the 26 files that hadn't had an individual pass since they were written (mostly 2026-08-02, toolbar recipes since 2025-12-22).

Dwell & hover

dwell-countdown.md
Rework — wrong number
Exemplars real: dwell_mode2.py, dwell_globals.py, dwell_constants.py
Explains the two-step countdown before a dwell-drag commits.
Finding: the "Drag Start Countdown" code sample hardcodes delays = [200, 200, 0]. The real constants in dwell_constants.py are COUNTDOWN_STEP_1_MS = 150 and COUNTDOWN_STEP_2_MS = 150. This is exactly the kind of bare value the recipe folder's own rule bans — and it's now factually wrong, which check-docs.js can't catch because it isn't attached to a constant name.
Fix: delete the literal array; point at COUNTDOWN_STEP_1_MS / COUNTDOWN_STEP_2_MS by name, same as the section two paragraphs later already does correctly.
dwell-drag.md
Rework — same wrong number
Exemplars real: Mode2State enum, dwell_mode2.py, dwell_globals.py — state names all match
The IDLE→COUNTDOWN→DRAGGING→COOLDOWN state machine for dwell-to-drag.
Finding: the same "Drag Start Countdown" snippet repeats the stale 200ms figure (real: 150ms). MOVEMENT_THRESHOLD = 15 and DRAG_RELEASE_TIME = 0.75 elsewhere in the doc are correctly left as pointers, not restated — only the one instance needs fixing.
Fix: same as dwell-countdown.md — replace 200ms with the constant name.
dwell-activation.md
Rework
Exemplars real: toolbar.html (dwellTimer, activateButton), toolbar-manager.js
Hover-a-toolbar-button-to-fire-it pattern.
Finding: exemplars check out, but the "Complete Template" code hardcodes dwellTime = options.dwellTime || 600 and cooldownTime || 800, and a "Timing Considerations" section prints invented ranges ("Fast 300-400ms", "Medium 500-700ms recommended") that don't correspond to any real constant.

dwell-click.md
Rework
Exemplars real: dwell_module.py handle_mode1() lines 478-543
Stationary-position dwell click (dwell mode 1).
Finding: the poll-loop shape matches the real code exactly, but "Timing Considerations" invents unsourced numbers ("Click Delay: Recommended 10-20ms") — the real code sleeps 0.04s (40ms) before mouseDown, not 10-20ms.
Fix: remove the three bare-value subsections; the rest of the recipe is an accurate template.
hover-to-lock-drag.md
Rework — self-contradicting
⚠️ already flagged in INDEX.md — the flag understates it
Drag handle on an overlay: hover to lock, then it follows the cursor.
Finding: the recipe's own "mistake this recipe exists to prevent" box says click-through overlays can never fire DOM mouseenter/mouseleave and mandates polling from the main process. But its own third exemplar, arrow-overlay.html, has a live dragHandle.addEventListener('mouseenter', ...) at line 460 that works. Worse: the actual current implementation — drag-overlay-runtime.js built on overlay-hover-poll.js's createOverlayHoverPoll (real constants HOVER_DWELL_MS=500, DRAG_STATIONARY_MS=500) — isn't named anywhere in the recipe.
Fix: rewrite the Electron section to point at drag-overlay-runtime.js + overlay-hover-poll.js instead of hand-rolled pseudocode; drop or caveat the "DOM events never fire" claim since there's a live counterexample in the recipe's own cited file.
mouse-hover-detection.md
Rework — downgrade from ✅
2 of 3 exemplars real; window-helpers.js has no hover logic
Detect cursor-over-region: polling vs. events.
Finding: scroll_module.py's polling functions and volume_module.py check out. But the third named exemplar, window-helpers.js, contains window creation/click-through helpers — no hover-polling logic at all. The real generic implementation this recipe should point to is overlay-hover-poll.js's createOverlayHoverPoll, which isn't mentioned.
Fix: swap the third exemplar for overlay-hover-poll.js.
