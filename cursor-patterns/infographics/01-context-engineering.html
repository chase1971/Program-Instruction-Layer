The Context Engineering System

Every app here is built with an AI assistant. This is the system that tells that assistant how I build things — so I stop repeating myself, and so features built months apart still look like the same app.

The whole idea in one sentence: anything I'd otherwise have to say out loud every session should live in a file the assistant reads automatically.

What it's for

I drive every app with a head-mounted mouse and a dwell click. That one fact creates a dozen requirements that aren't obvious from looking at the code — and an assistant that doesn't know them will confidently build something I can't use.

Buttons can't be hover-only. I can't reliably hover something without also clicking it. Anything that only appears on hover is invisible to me in practice.
Modals can't close when you click outside them. My cursor drifts. A dialog that closes on a stray click will destroy half-finished work.
Timers need generous thresholds. The cursor wobbles a few pixels even when I'm holding still. Anything tighter than about 12 pixels will never trigger.

None of that is guessable. Written down once, it applies forever. That's the entire value proposition.

How it's built — three layers

Everything lives in one of three places, and which place you choose decides whether the rule actually fires.

From always-loaded to read-if-asked

Higher means more reliable. Lower means more detail.
🔒 Always on — AGENTS.md at the rootLoaded in every session, everywhere in the tree. The rules I break most often, and the shortest possible version of each. Kept deliberately small, because everything here competes for attention.
🎯 Scoped rules — one folder per appLoaded only when a matching file is open. A rule about modals appears when I'm editing a modal and stays silent otherwise. This is where most rules should live.
📄 Reference docs — read when relevantDeep background, full explanations, pattern libraries. Only read if something above points at them — so anything down here that isn't linked is effectively invisible.
The one thing that goes wrong most: good documentation that nothing links to. Sixteen well-written pattern docs sat unreferenced for months — not wrong, just unreachable. Writing more wouldn't have helped. One index file did.

What makes a rule actually work

Rules that get followed all look the same. Rules that get ignored are usually missing one of these.

Say why. "I use a head-mouse with a dwell click." A rule without a reason reads like a preference — and preferences get overridden.
Name the exact thing to reuse. Not "use a hook" — this one, at this path. Vagueness is what produces a second copy of something that already existed.
Point at a real file to copy. A working example beats a description. Descriptions drift out of date quietly; a file path breaks loudly.
Say what breaks if it's ignored. This is what stops a future session from deleting something that looks unnecessary but isn't.
Same rule for numbers. Never leave a bare value like 450 in the code. Give it a name and a comment saying what it's compensating for. Bare numbers get "tidied up" by the next assistant, and then the bug comes back.

Keeping it maintained

Two habits and one command. That's the whole maintenance story.

When I notice something, say it immediately. Not "I'll write that down later" — later never comes, and the reason gets forgotten even if the rule doesn't.
When a correction repeats, move it up a layer. Saying the same thing twice means it's sitting too low to fire. The fix isn't rewording it — it's promoting it.
Run the health check when docs move. node scripts/check-docs.js — finds broken links, unreachable docs, duplicate copies, and rules that aren't indexed anywhere.

Adding something — just say it

I don't write these files. I say one sentence and the assistant decides where it belongs, writes it properly, and deletes whatever weaker version it replaces.

The middle row matters most. Repeating myself isn't a nuisance to tolerate — it's evidence that a rule is filed too low to fire, and the signal to promote it.

What's not worth capturing: one-off instructions ("make this button blue"), anything the code already shows, and vague preferences with no failure attached. If I can't say what goes wrong without it, it isn't a rule yet.

Starting a new app

One sentence connects a brand-new folder to everything above. The recipe asks three questions, then builds the whole scaffold.

Initialize a new app called [name]
It asks three things. The name and one-line purpose, which kind of app it is, and where to put it. Nothing gets created until I confirm.
It picks a variant. A teaching/math app, a utility tool, or a desktop overlay. The variant decides the folder structure and the starting configuration.
It scaffolds the connection points. An orientation file so the assistant knows what the app is, a guidelines file for app-specific quirks, a session log, and the config that hooks into the shared standards.
Then I register it. Add it to the app index so its name resolves later, and to the launcher registry if it needs a shortcut. Skipping this is why an app becomes hard to find months later.
Why the orientation file is the important one. It's not the rules themselves — it's the index: what this app is, which rules apply and when, where the good examples are. Without it, an app's scoped rules are invisible to half my tooling. It's the single file that connects a new app to the whole system.

If you remember five things

One source of truth per idea. Four versions of the same setting is a bug. One version with documented exceptions is a system.
Point at real code, not descriptions. Examples stay accurate as things move. Prose quietly stops being true.
Always write down the reason. The reason is what survives the next session — it's what separates a constraint from a preference.
Put the rule where the work happens. Scoped to the files it governs: silent when irrelevant, unmissable when it isn't.
If it must never break, automate it. A check that blocks the mistake beats a paragraph asking nicely.
