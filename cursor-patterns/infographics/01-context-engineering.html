Working with AI assistants

Context Engineering

A method for teaching an AI coding assistant the rules of a project — so the same instructions don't have to be repeated every session, and work produced months apart still looks like it belongs together.

The whole idea in one sentence: anything that would otherwise be said out loud at the start of every session should live in a file the assistant reads automatically.

The problem it solves

An assistant can read every line of a codebase and still miss the things that matter most — because the most important constraints usually aren't visible in the code at all.

Requirements that live outside the code. Accessibility needs, performance budgets, compliance rules, hardware limits. Nothing in the source says a constraint exists, so a reasonable-looking change can quietly violate it.
Conventions that only matter in aggregate. Any single choice is defensible on its own. It's the fifth slightly-different version of the same component that becomes the problem — and that's invisible from inside any one file.
Fixes that look like clutter. Hard-won solutions often read as redundant code. Without a record of what they prevent, they get "cleaned up," and the original bug comes back.

None of these are guessable from context. Written down once, they apply indefinitely. That's the entire value proposition.

How it's structured — three layers

Guidance lives in one of three places, and the choice of layer determines whether a rule actually reaches the assistant at the moment it's needed.

From always-loaded to read-only-if-asked

Higher is more reliable. Lower holds more detail.
🔒 Always on — one file at the project rootLoaded in every session. Holds only the rules broken most often, in the shortest form that works. Kept deliberately small, because everything here competes for attention with everything else.
🎯 Scoped rules — attached to file patternsLoaded only when a matching file is open. A rule about database queries appears while editing a query and stays silent otherwise. Most rules belong here.
📄 Reference docs — read when relevantDeep background and full explanations. Only reached if something above points at them — so anything down here that isn't linked is effectively invisible.
The most common failure by far: well-written documentation that nothing links to. It isn't wrong — it's unreachable, which produces exactly the same result as not existing. Writing more rarely fixes this. Adding an index does.

What separates a rule that works from one that gets ignored

Rules that hold up all share the same four parts. Rules that quietly stop being followed are usually missing one of them.

State the reason. A rule without a justification reads as a preference — and preferences get overridden the moment they're inconvenient.
Name the exact thing to reuse. "Use the existing helper" is not actionable. Naming the specific one, at its specific location, is. Vagueness is what produces the duplicate.
Point at a working example. A real file beats a description of one. Descriptions drift out of date silently; a reference to something that moved breaks visibly.
Say what breaks without it. This is what stops a future session from removing something that looks unnecessary but is load-bearing.
The same principle applies to constants. A bare number in the code carries no argument for its own existence, so it gets adjusted or removed during cleanup. Give it a name and a comment explaining what it compensates for, and it survives.

Keeping it healthy

Two habits and one automated check. That is the entire maintenance burden.

Record it at the moment it's noticed. Deferring means it doesn't get written down — and even when it does, the reasoning behind it has already been lost.
When a correction repeats, move it up a layer. Having to give the same instruction twice means it's filed too low to fire. The fix is promotion, not rewording.
Check reachability whenever docs move. An automated pass for broken links, unreferenced files, duplicated content, and rules missing from an index catches decay long before anyone notices it by hand.

Adding something new

The person with the knowledge shouldn't have to decide where it belongs or write the file. They state it in one sentence; the assistant handles placement, wording, and cleanup of whatever it replaces.

The middle row carries the most weight. A repeated correction isn't an annoyance to absorb — it's evidence that a rule sits too low in the structure to fire, and the clearest signal available that it should be promoted.

What isn't worth capturing: one-off task instructions, anything already evident from the code itself, and preferences with no stated failure mode. If the consequence of ignoring it can't be named, it isn't a rule yet — it's an opinion.

Connecting a new project

A new codebase starts with none of this. A single scaffolding step wires it into everything above, and skipping that step is why a project drifts out of the system months later.

Confirm the essentials first. What it is in one line, which category it falls into, and where it lives. Nothing gets generated until that's agreed — the wrong scaffold is more expensive than none.
Generate from a template, not from scratch. The category determines the structure and starting configuration, so equivalent projects stay genuinely equivalent instead of merely similar.
Create the orientation file. Not the rules themselves — an index. What this project is, which rules apply and when, and where the reference examples are.
Register it where things get looked up. Add it to whatever index resolves project names and locations. Skipping this is the single most common reason something becomes hard to find later.
Why the orientation file matters most. Tooling differs in what it loads automatically — one assistant may pick up scoped rule files on its own while another never does. The orientation index is what makes a project's rules discoverable regardless, which is what actually connects it to the wider system.

Where the cost actually is

Most effort to reduce an assistant's running cost gets aimed at the instruction files — which is almost always the wrong target. Measuring first gives a very different answer.

2–3%
Share of the context window used by always-loaded rules — and it's cached after the first message, so it's paid roughly once, not per step.
~10×
Reduction when a task that was figured out the first time becomes a script that's simply run the next time.
zero
Tool calls needed when the answer was written down after the first run. Nothing beats not having to look.
~2,000
Tokens burned by a single broad search that returns build output and dependency folders alongside real source.

Figures from one measured project, not universal constants — but the ranking they imply has held up consistently.

The expensive part is what gets written, not what gets read. Text the assistant produces is billed at a premium and is never cached. A session that generates nine throwaway scripts to figure something out costs far more than one that runs a saved script — the difference is mostly authorship, not reading.
Repeated context is nearly free; fresh results are not. The conversation so far is cached and re-read cheaply. Each new tool result enters at full price. This inverts a common instinct: one long focused session is usually cheaper than several short ones, because restarting throws the cache away and pays for the setup again.
The practical consequence. Trimming rule files is visible, satisfying, and worth very little. Converting a solved problem into a script, and its answer into a written record, is worth an order of magnitude more. Optimize what recurs, not what's merely large.

When the tooling quietly lies

Every layer above assumes the assistant can find what already exists. That assumption is worth testing, because when it fails it fails silently — and silence is indistinguishable from a correct answer.

The most dangerous result is an empty one. A configuration meant to limit which files got backed up also determined which files could be searched. A search across the whole project returned no matches — not because nothing matched, but because everything had been filtered out before the search began. The assistant had no way to tell those apart.

The damage isn't the wasted search. It's what a confident "nothing found" leads to next: the rule that matters most — check whether this already exists before building it — inverts into permission to build a second copy. Duplicate implementations are the expensive failure this whole system exists to prevent, and a broken search manufactures them.

Treat "no results" as a claim, not a fact. Before concluding something doesn't exist, confirm the search can see anything at all — search for something known to be present. An empty result should trigger a check of the filter first.
Verify what each tool actually skips. Tools that look interchangeable often aren't: some honor ignore files, some honor a different set, some honor none. This is worth testing directly rather than assuming, because every assumption here is invisible until it's wrong.
Keep exclusions separate from other configuration. When one file controls both what's stored and what's visible, a reasonable change to one silently breaks the other. Search visibility deserves its own explicit, commented configuration.
Exclude by structure, not by request. A note asking the assistant to avoid a folder depends on it being read and followed every time. A filter that removes the folder from results cannot be forgotten. Prefer the mechanism over the reminder.
The general lesson. Guidance is only as good as the assistant's ability to act on it. A rule that says "look before you build" is worthless if looking returns nothing — so the retrieval path deserves the same scrutiny as the rules themselves, and should be tested rather than trusted.

Five things worth remembering

One source of truth per concept. Four versions of the same setting is a defect. One version with documented exceptions is a system.
Reference real code, not descriptions of it. Examples stay accurate as things move. Prose quietly stops being true and gives no indication that it has.
Always record the reason. The reason is what survives into the next session — it's what distinguishes a constraint from a preference.
Put the rule where the work happens. Scoped to the files it governs: silent when irrelevant, unmissable when it isn't.
If it must never break, automate it. A check that blocks the mistake outperforms a paragraph asking politely.
