How the AI Knows the Rules

Every app in this tree is built with an AI assistant. This is the system that tells that assistant how you build things — so you stop re-explaining the same requirements every session, and so two features built six months apart still look like the same app.

Why this matters: the expensive failure isn't the AI writing bad code — it's the AI writing reasonable code that ignores a constraint you never wrote down. A button that only responds to hover. A modal that closes when the cursor drifts. A fifth copy of a mechanism that already existed four times. Every one of those is a missing sentence in a file, not a missing instruction in a chat.

The problem this solves

You drive every app with a gyro head-mounted mouse and a dwell click. That single fact generates a dozen non-obvious code requirements — and an AI that doesn't know it will confidently build something you can't use.

✗ Without a context layer

Every session starts cold You re-explain the head mouse, the dwell click, the 12px threshold, the no-backdrop-dismiss rule.
You forget one The AI builds a hover-only tooltip. It's invisible to you in practice.
Drift compounds Four hover mechanisms, four different timings, none aware of the others.

✓ With one

The constraint lives in a file The AI reads it before it writes the first line.
You say four words “Make it dwell-friendly” resolves to one hook, one timing file, one exemplar.
Rules that must never break get teeth A lint rule or a commit hook enforces it, so it can't quietly rot.

The capture ladder — push every lesson as high as it will go

When a bug gets fixed or a correction repeats, it should end up on the highest rung it can reach. Higher rungs fire automatically and can't be skipped; lower rungs rely on someone choosing to read them. Graduating to a higher rung means deleting the lower copy — prose that a lint rule already enforces is just noise.

Five rungs, strongest first

Ask of any rule: what's the highest rung this could live on?
1
Make it structurally impossibleOne owner, or an API that can't be misused. Example: only usePersistedState.ts may touch localStorage — everything else is a lint error. The rule can't be forgotten because the shape of the code won't allow it.
2
A lint rule or a testFires on every save or every commit. Example: files warn at 700 lines and are blocked at 800.
3
A glob-scoped contractA rule file that loads only when you open matching files. Costs nothing when irrelevant, always present when it matters. This is the sweet spot for most patterns.
4
An always-on ruleLoaded every session, so it competes for attention with everything else. Keep the total budget small — roughly 200 lines across all of them.
5
An on-demand documentRead only when someone decides it's relevant — which is a judgment call, and therefore the rung where knowledge quietly dies. Fine for deep background; wrong for a rule that must always fire.
The trap: writing a beautiful 578-line document (rung 5) for your most important constraint, and a one-line lint rule (rung 2) for a minor one. Importance should decide the rung — not how much you enjoyed writing it.

How a rule actually reaches the AI

Four hops, from “always loaded” down to “only if someone opens it.” The critical detail is that the two assistants don't load the same things.

1 · Root AGENTS.md auto-loaded
The entry point for every session anywhere in the tree. Holds the most-violated rules, the ask-before-you-assume posture, the dwell summary, and the end-of-session protocol. CLAUDE.md is a one-line stub that imports it, so both assistants get the same baseline.
2 · App CLAUDE.md read on entry
One per app. Not the rules themselves — an index: what this app is, which rule files exist and when they apply, which docs to read for which topic, where the exemplars are.
3 · Glob-scoped .mdc rules Cursor Claude Code
The workhorses. Cursor loads them automatically when a matching file is open. Claude Code does not — which is exactly why hop 2 exists. If an app has rule files but no CLAUDE.md indexing them, they are invisible to half your tooling.
4 · On-demand docs only when asked
Deep background — architecture notes, integration write-ups, pattern libraries. Reachable only if something above points at them. An unreferenced document is functionally deleted.
The single most common failure in this system: good documentation that nothing links to. Sixteen well-written interaction patterns sat in the toolbar repo for months, reachable from no index, read by nobody. The fix wasn't writing more — it was writing one index file.

What a good rule file contains

The exemplar in this tree is studio-dwell-mechanics.mdc. Every rule worth writing has these five ingredients — miss any one and the rule gets ignored, misapplied, or “cleaned up” by the next session.

Why it exists, in one sentence. “Chase uses a gyro head-mouse + dwell click.” A rule without a reason reads like a preference, and preferences get overridden.
The single implementation, named. Not “use a hook” — this hook, at this path. Ambiguity is what produces the second copy.
An exemplar file to copy. Pointing at real working code beats describing it. Prose drifts from the codebase; a file path doesn't.
Non-negotiables, each with the bug it prevents. “Leave handlers are no-ops because wobble fires them constantly.” This is what stops a future session from deleting code that looks redundant.
An anti-pattern list. The failure modes stated as failures. “Tight 2px thresholds — never latch for a head-mouse.”
Same principle, applied to numbers: never write a bare constant. JIGGLE_MODE1_TO_PAUSE_MAX_NET_DISPLACEMENT = 40 survives because the comment above it explains that head-mouse navigation oscillates. A bare 40 gets “simplified” by the next agent, and the bug comes back.

Case study: four answers to “how long is a dwell?”

The clearest example of what happens without a source of truth. Four independent implementations grew up in four repos — each one reasonable on its own, none aware of the others.

Three of those four differences are legitimate — and that's the point. The system click must be fast because it replaces every click you make. The drag latch is deliberately slower than the system click so a normal click isn't mistaken for a drag. A tooltip should be slow because it means “I paused to read.” The fourth is simply wrong: numbers written to illustrate an example, never measured, sitting in a document where they look authoritative.

The finding nobody had written down: those two layers run at the same time, on the same cursor. When you rest on a drag handle, the toolbar fires a real click at 250 ms — 200 ms before the in-app latch arms. No document in either repo mentioned that the other system was running. That gap, not any single number, was the actual defect.

Enforcement: rules with teeth

A rule nobody can violate beats a rule everybody agrees with. But enforcement added carelessly locks you out of your own repo — so it arrives in tiers, with an escape hatch for what's already broken.

TierWhat it doesWhen it fires
Editor warningAdvisory squiggle at 700 linesAs you type — informational, never blocks
Commit blockRefuses the commit past 800 linesOn git commit — the real gate
GrandfatheringFiles already over the cap warn instead of failingAutomatically, by comparing against the last commit

That third row is what makes the second row survivable. A repo with a 2,157-line file can't adopt a hard 800-line cap on day one — every commit would fail and the hook would be deleted within a week. Instead, existing offenders are recorded and warn; only new files and files that newly cross the line are blocked. The cap holds the line without demanding a refactor you didn't schedule.

The machinery, in detail

Why every app is its own repo — and what that costs
Each app is an independent repository, not a monorepo. That keeps them separately cloneable and separately versioned, but it means shared tooling has to be copied into each one rather than referenced from a parent folder — a hook that reaches outside its own repo breaks the moment that repo is cloned on its own. Duplicating a build script across independent repos is acceptable; duplicating an app concept is the thing to avoid.
“Grep before you build” — the rule that prevents the fifth copy
Before creating any new hook, service, logger, registry, or state store, search for what it would replace — including in sister apps. If something exists, extend it. If you'd be creating a second implementation of an existing concept, stop and ask rather than deciding alone. Parallel mechanisms are the main way a tree like this accumulates inconsistency: each one looks like “I solved the task” and reads later as “nothing fits together.”
Why documents get tombstones instead of deletions
When a document is superseded, it's replaced with a few lines pointing at the live version — “content merged into X; do not maintain this file.” A deleted file leaves a dangling link; a tombstone redirects. The same applies to docs describing something that was never built: they get a banner saying so, because a plausible-looking design sketch is more dangerous than a missing file.
The index that resolves app names
A dedicated file maps every name you might say — nicknames, legacy folder names, deprecated duplicates — to a canonical path. Without it an assistant searches the filesystem and finds three folders with similar names, one of which is a frozen copy. With it, the lookup is a table read.
Frozen apps
An app can be explicitly detached: no routine scans, no edits, no git sync until it's unfrozen. This is recorded in both an always-on rule and a marker file in the app itself, so an assistant hits the signal from either direction. Frozen apps stay readable as reference exemplars — they just don't get touched.

The shape of the whole thing

Five ideas carry the entire system. Everything else is application.

One source of truth per concept. Four timing tables is a bug. One table with four documented exceptions is a system.
Point at code, not prose. An exemplar file path stays accurate as the codebase moves. A described pattern drifts the day after it's written.
Record the reason, not just the rule. The reason is what survives contact with the next session — it's the difference between a constraint and a preference.
Put the rule where the work happens. Scoped to the files it governs, so it costs nothing when irrelevant and is unmissable when it isn't.
Give the important ones teeth. If it must never break, a lint rule or a commit hook — not a paragraph.
